## 1. المشكلة: من يملك المفتاح؟ | The Problem: Who Owns the Key?

### المشكلة في النموذج الحالي

```
BDCP اليوم:
────────────
Alice (مستشفى A) يملك ClientKey الوحيد
  └── كل النتائج تمر عبر Alice
  └── لا أحد غير Alice يفك التشفير
  └── Bob (مستشفى C) يرسل بياناته لكن لا يرى النتيجة
  └── Sponsor (الجهة الممولة) لا يرى شيئاً
```

هذا يعمل في الـ Demo. لكنه يفشل في الدراسات الحقيقية لـ 5 أسباب:

| # | السيناريو | المشكلة في النموذج الحالي |
|---|----------|--------------------------|
| 1 | **تغادر PI المؤسسة** | المفتاح يغيب معها — لا أحد يستطيع فك نتائج الدراسة |
| 2 | **الـ Sponsor يريد النتائج** | لا يستطيع — هو ليس Alice |
| 3 | **تنسحب مستشفى من الدراسة** | لا توجد آلية لإلغاء وصولها |
| 4 | **يدّعي أحد المشاركين الغش** | لا يوجد سجل تدقيق يثبت من فك تشفير ومتى |
| 5 | **تنتهي الدراسة** | لا توجد سياسة لحذف المفاتيح والبيانات |

### 6 أسئلة يجب أن تجيب عليها الحوكمة

```
┌─────────────────────────────────────────────────────────────┐
│                     GOVERNANCE QUESTIONS                      │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  1. Ownership:  من يملك مفاتيح الدراسة؟                       │
│                                                              │
│  2. Access:     من يستطيع رؤية النتائج؟                       │
│                                                              │
│  3. Consent:    من يوافق على بدء الدراسة وإنهائها؟             │
│                                                              │
│  4. Revocation: كيف نلغي صلاحية جهة مشاركة؟                   │
│                                                              │
│  5. Audit:      كيف نثبت من فك التشفير ومتى؟                  │
│                                                              │
│  6. Retention:  متى تُحذف المفاتيح والبيانات والنتائج؟         │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

## 2. أصحاب المصلحة | Stakeholders

### 2.1 الأطراف في أي دراسة مشتركة

```
                        ┌─────────────────────┐
                        │    Study Sponsor     │
                        │   (e.g., NIH, Pfizer)│
                        │        يموّل        │
                        └──────────┬──────────┘
                                   │
        ┌──────────────────────────┼──────────────────────────┐
        │                          │                          │
   ┌────▼────┐              ┌──────▼──────┐            ┌─────▼────┐
   │ Hospital A │              │  Hospital B   │            │ Hospital C │
   │ (Alice)    │              │  (Relay)      │            │  (Bob)     │
   │            │              │               │            │            │
   │ PI + Data  │              │  PI + Data    │            │ PI + Data  │
   │ + IRB      │              │  + IRB        │            │ + IRB      │
   └─────┬──────┘              └──────┬────────┘            └─────┬──────┘
         │                           │                          │
         └───────────────────────────┼──────────────────────────┘
                                     │
                              ┌──────▼──────┐
                              │  Regulator   │
                              │  (FDA, OCR)  │
                              └─────────────┘
```

### 2.2 مصالح كل طرف

| الطرف | يريد | لا يريد | العلاقة مع المفاتيح |
|-------|------|---------|-------------------|
| **Principal Investigator (PI)** | رؤية النتائج الإحصائية للدراسة | كشف سجلات مرضاه | يملك حق فك التشفير |
| **Data Manager** | تشغيل النظام، إرسال ciphertexts | مسؤولية امتثال شخصية | لا يملك مفتاحاً |
| **IRB Officer** | الموافقة على الدراسة | مخالفة HIPAA | يراجع فقط |
| **Study Sponsor** | حصوله على نتائج الدراسة التي موّلها | انتظار موافقة Alice | يجب أن يرى النتائج النهائية |
| **Regulator (FDA/OCR)** | التحقق من نزاهة الدراسة | كشف بيانات المرضى | يطلب سجل التدقيق |
| **Participating Hospital** | حماية سجلات مرضاهم | المسؤولية القانونية عن بيانات الآخرين | يملك بياناته فقط |

### 2.3 مبدأ الحد الأدنى من الوصول | Principle of Least Privilege

```
كل طرف يملك فقط:
─────────────────
PI:          المفتاح الخاص بفك نتائج مؤسسته فقط
Sponsor:     المفتاح الخاص بالنتائج المجمّعة فقط (ليس الفردية)
Data Manager: لا يملك أي مفتاح — ciphertexts فقط
Relay:       لا يملك أي مفتاح — ciphertexts فقط، ولا يفك تشفير
IRB:         لا يملك مفتاحاً — يراجع السياسات فقط
Regulator:   لا يملك مفتاحاً — يراجع audit log فقط
```

## 3. نماذج حوكمة المفاتيح | Key Governance Models

### 3.1 النموذج A: مالك واحد (Single-Key — الوضع الحالي)

```
Alice ─── يملك ClientKey الوحيد
        │
        ├── يفك تشفير نتائج الجميع
        └── نقطة فشل وحيدة
```

| الميزة | القيمة |
|--------|--------|
| **البساطة** | ⭐⭐⭐⭐⭐ |
| **الأمان** | ⭐⭐ — نقطة فشل وحيدة |
| **المرونة** | ⭐ — لا يشارك الآخرون النتائج |
| **مناسب لـ** | التجارب التقنية، Demos |

### 3.2 النموذج B: المفتاح المشترك (Shared Key — فريق واحد)

```
Study Team ─── ClientKey يُشارك بين أعضاء الفريق
             │
             ├── عبر قناة آمنة (e.g., Vault / USB في خزنة)
             ├── أي عضو يستطيع فك التشفير
             └── خطر: أي عضو يستطيع فك تشفير أي شيء
```

| الميزة | القيمة |
|--------|--------|
| **البساطة** | ⭐⭐⭐ |
| **الأمان** | ⭐⭐⭐ — يعتمد على ثقة الفريق |
| **المرونة** | ⭐⭐⭐ — أي عضو يرى النتائج |
| **مناسب لـ** | فرق بحثية صغيرة، مراكز أكاديمية |

### 3.3 النموذج C: تشفير متعدد المفاتيح (Per-Party Key — BDCP محسّن)

```
كل طرف يملك مفتاحه الخاص:
    Alice ─── ClientKey_A ← يفك تشفير نتائج A فقط
    Sponsor ─ ClientKey_S ← يفك تشفير النتائج المجمّعة فقط
    لا أحد ─── يمكنه فك تشفير نتائج طرف آخر

الـ Relay يقوم بتجميع ciphertexts لكل مفتاح على حدة.
```

| الميزة | القيمة |
|--------|--------|
| **البساطة** | ⭐⭐⭐ — أكثر تعقيداً لكنه طبيعي |
| **الأمان** | ⭐⭐⭐⭐⭐ — كل طرف يرى ما يخصه فقط |
| **المرونة** | ⭐⭐⭐⭐ — Sponsor يرى المجمّع، PI يرى مؤسسته |
| **مناسب لـ** | الدراسات السريرية متعددة المراكز |

### 3.4 النموذج D: تشفير عتبي (Threshold Decryption — أعلى أمان)

```
ClientKey مقسّم إلى N شارة (Shamir Secret Sharing)
    ├── أي M من N (e.g., 3 من 5) يجب أن يجتمعوا لفك التشفير
    ├── لا يوجد فرد واحد يملك المفتاح الكامل
    └── آمن حتى لو اخترقت M-1 من الأطراف
```

| الميزة | القيمة |
|--------|--------|
| **البساطة** | ⭐ — معقد، يحتاج تنفيذ Shamir أو DKG |
| **الأمان** | ⭐⭐⭐⭐⭐ — أعلى نموذج |
| **المرونة** | ⭐⭐ — بطيء، يحتاج توافق |
| **مناسب لـ** | وكالات حكومية، تحالفات عالية الحساسية |

### 3.5 المقارنة | Comparison

| النموذج | الأمان | البساطة | المرونة | السرعة | التكلفة الهندسية |
|---------|--------|---------|---------|--------|-----------------|
| A: Single-Key | 3/10 | 10/10 | 2/10 | 10/10 | صفر — موجود |
| B: Shared Key | 5/10 | 7/10 | 6/10 | 9/10 | يوم واحد |
| **C: Per-Party Key** | **9/10** | **8/10** | **9/10** | **8/10** | **أسبوعان** |
| D: Threshold | 10/10 | 3/10 | 7/10 | 5/10 | شهران+ |

## 4. النموذج الموصى به | Recommended Model

### اختيارنا: النموذج C — Per-Party Key + Layer من المفاتيح التعاقدية

```
لماذا C وليس A أو D؟
────────────────────────
A: بسيط لكن يفشل في أي دراسة حقيقية (>2 أطراف)
D: آمن جداً لكن معقد قبل أول عميل

C: توازن مثالي بين الأمان والبساطة
   ويمكن ترقيته لـ D لاحقاً
```

### 4.1 معمارية Per-Party Key

```
                           ┌──────────────────────┐
                           │    Key Server         │
                           │  (يديره Sponsor أو    │
                           │  CRO مستقل)           │
                           │                       │
                           │  لكل دراسة:            │
                           │  ├── Master Key Pair  │
                           │  ├── Per-Party Keys   │
                           │  └── Policy Config    │
                           └──────────┬───────────┘
                                      │
              ┌───────────────────────┼───────────────────────┐
              │                       │                       │
        ┌─────▼──────┐         ┌──────▼──────┐         ┌─────▼──────┐
        │ Hospital A  │         │  Hospital B  │         │ Hospital C  │
        │             │         │  (Relay)     │         │             │
        │ ClientKey_A │         │  لا مفتاح    │         │ ClientKey_C │
        │ يرى نتائج A │         │  ciphertexts │         │ يرى نتائج C │
        └─────────────┘         └─────────────┘         └─────────────┘
                                      │
                                      │ النتائج المجمّعة مشفّرة بمفتاح Sponsor
                                      ▼
                             ┌─────────────────┐
                             │  Study Sponsor   │
                             │  ClientKey_S     │
                             │  يرى المجمّع فقط │
                             └─────────────────┘
```

### 4.2 كيف يعمل هذا في BDCP

```
1. إنشاء الدراسة:
   ├── Sponsor ينشئ الدراسة مع Key Server
   ├── Key Server يولّد:
   │   ├── Master Key Pair (للتوقيع)
   │   ├── ClientKey_A + PublicKey_A ← لأليس
   │   ├── ClientKey_C + PublicKey_C ← لبوب
   │   └── ClientKey_S + PublicKey_S ← للراعي (مجمّع فقط)
   └── توزع المفاتيح عبر قنوات آمنة (Vault / HSM)

2. تشفير البيانات:
   ├── Alice تشفر بياناتها بـ PublicKey_A وتُرسل ciphertext للـ Relay
   ├── Bob يشفر بياناته بـ PublicKey_C ويُرسل ciphertext للـ Relay
   └── الـ Relay لا يملك أي مفتاح — فقط ciphertexts

3. الحساب:
   ├── الـ Relay ينفذ add(ciphertext_A, ciphertext_C)
   ├── الـ Relay يشفر النتيجة المجمّعة بـ PublicKey_S (للـ Sponsor)
   └── الـ Relay يرسل ciphertext_A_encrypted + ciphertext_C_encrypted + result_S

4. فك التشفير:
   ├── Alice تفك ciphertext_A بـ ClientKey_A ← ترى نتائج مستشفاها فقط
   ├── Bob يفك ciphertext_C بـ ClientKey_C ← ترى نتائج مستشفاه فقط  
   └── Sponsor يفك result_S بـ ClientKey_S ← يرى المجمّع الكلي فقط
```

### 4.3 ماذا نحتاج لبناء هذا في BDCP؟

| المكون | الحالة | الجهد |
|--------|--------|-------|
| **Key Server** | 🆕 جديد | أسبوعان |
| **توزيع المفاتيح** (Vault/PKCS#11) | 🆕 جديد | أسبوع |
| **تعديل FheEngine** — support per-party keys | 🔧 تعديل | 3 أيام |
| **تعديل Relay** — تشغيل ciphertexts متعددة المفاتيح | 🔧 تعديل | 3 أيام |
| **إضافة ClientKey_S للنتائج المجمّعة** | 🆕 جديد | أسبوع |
| **Audit Logging** | 🆕 جديد | أسبوع |

الإجمالي: **~5-6 أسابيع**

### 4.4 البديل الخفيف (لأول عميل — V0.1)

إذا كان أول عميل يقبل نموذجاً أبسط لدراسة تجريبية:

```
V0.1 — نموذج مؤقت لأول PoC مجاني:
─────────────────────────────────
نستخدم النموذج A (Single-Key) مع ضمانات تعاقدية:
  ├── Alice = Sponsor نفسه (يدفع ويرى النتائج)
  ├── عقد قانوني ينص على أن المفتاح ملك الدراسة
  └── يتم إتلاف المفتاح بنهاية الدراسة

V1.0 — نموذج Per-Party Key للعملاء المدفوعين:
  └── نبني Key Server + Audit Logging
```

هذا يسمح لنا بإغلاق أول عميل خلال 4-6 أسابيع مع عقد قانوني
يحمي الجميع، ثم نبني الحوكمة التقنية بعد الإيراد الأول.

## 5. دورة حياة المفتاح | Key Lifecycle

### 5.1 المراحل | Stages

```
                       ┌──────────┐
                       │  إنشاء   │
                       │ Creation │
                       └────┬─────┘
                            │
                            ▼
                       ┌──────────┐
                       │  توزيع   │
                       │Distribution│
                       └────┬─────┘
                            │
                            ▼
                       ┌──────────┐
                       │  تفعيل   │
                       │ Activation│
                       └────┬─────┘
                            │
                    ┌───────┴───────┐
                    │               │
                    ▼               ▼
              ┌──────────┐   ┌──────────┐
              │ استعمال  │   │  تدوير   │
              │  Usage   │   │ Rotation │
              └────┬─────┘   └────┬─────┘
                   │              │
                   └───────┬──────┘
                           │
                           ▼
                    ┌──────────┐
                    │  إبطال   │
                    │ Revocation│
                    └────┬─────┘
                         │
                         ▼
                    ┌──────────┐
                    │  إتلاف   │
                    │Destruction│
                    └──────────┘
```

### 5.2 سياسات كل مرحلة | Policies Per Stage

| المرحلة | السياسة | المسؤول |
|---------|---------|---------|
| **Creation** | يُنشأ المفتاح داخل HSM أو Vault. لا يُصدّر أبداً في plaintext. | Key Server / Sponsor |
| **Distribution** | يُوزّع عبر قناة مشفّرة: Vault JWT / PKCS#12 بحماية كلمة سر / HSM مُدار | Key Server |
| **Activation** | يُفعّل المفتاح فقط بعد توقيع DPA من جميع الأطراف | Sponsor |
| **Usage** | يُستخدم المفتاح فقط لفك نتائج الدراسة المحددة | PI / Sponsor |
| **Rotation** | إذا طالت الدراسة (>12 شهراً)، يُدرّع المفتاح كل 6 أشهر | Key Server |
| **Revocation** | يُبطل المفتاح فوراً إذا انسحب طرف أو اخترق | Sponsor |
| **Destruction** | يُحذف المفتاح بعد 30 يوماً من انتهاء الدراسة (أو حسب DPA) | Key Server |

## 6. صلاحيات الوصول | Access Control

### 6.1 مصفوفة الصلاحيات (RBAC) | Permission Matrix

| الدور | إنشاء دراسة | رفع بيانات | تنفيذ حساب | رؤية نتائج مؤسسته | رؤية نتائج مجمّعة | إبطال مفاتيح | حذف دراسة |
|-------|-----------|-----------|-----------|-----------------|------------------|-------------|----------|
| **PI** (طبيب باحث) | ✅ | ❌ | ❌ | ✅ | ✅ (مجمّع فقط) | ❌ | ❌ |
| **Data Manager** | ❌ | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |
| **Sponsor** | ✅ | ❌ | ❌ | ❌ | ✅ (مجمّع فقط) | ✅ | ✅ |
| **Relay Operator** | ❌ | ❌ | ✅ | ❌ | ❌ | ❌ | ❌ |
| **IRB** | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |
| **Auditor** | ❌ | ❌ | ❌ | ✅ (قراءة audit logs فقط) | ❌ | ❌ |

### 6.2 مستويات النتائج | Result Levels

```
كل نتيجة تُصنّف بـ "تاغ" يحدد من يستطيع فك تشفيرها:
─────────────────────────────────────────────────────

تاغ: "per-institution"
  └── يفكها ClientKey الخاص بالمؤسسة فقط
  └── مثال: complication_rate لمستشفى A

تاغ: "per-institution-shareable"
  └── يفكها ClientKey الخاص بالمؤسسة + Sponsor
  └── مثال: total_count (ليس حساساً)

تاغ: "pooled"
  └── يفكها ClientKey الخاص بـ Sponsor فقط
  └── مثال: pooled_complication_rate

تاغ: "audit"
  └── غير مشفّر (لكن بدون معلومات تعريفية)
  └── مثال: عدد السجلات التي تم رفعها
```

### 6.3 قواعد الوصول (Policy as Code)

```
study_policy = {
    "id": "BDCP-2026-001",
    "parties": [
        {"id": "hospital_a", "role": "alice",   "can_decrypt": ["per-institution"]},
        {"id": "hospital_b", "role": "relay",   "can_decrypt": []},
        {"id": "hospital_c", "role": "bob",     "can_decrypt": ["per-institution"]},
        {"id": "sponsor",    "role": "sponsor", "can_decrypt": ["pooled", "per-institution-shareable"]},
        {"id": "auditor_x",  "role": "auditor", "can_decrypt": []},
    ],
    "m_of_n": null,  // لا حاجة لـ threshold حالياً
    "retention_days": 365,
    "require_rotation_days": 180,
}
```

## 7. الإبطال والانسحاب | Revocation & Withdrawal

### 7.1 سيناريو انسحاب مستشفى من الدراسة

```
مستشفى C يقرر الانسحاب في منتصف الدراسة ─── ماذا يحدث؟
────────────────────────────────────────────────────────

1. Sponsor يُصدر Revocation Command:
   POST /api/v1/study/BDCP-2026-001/revoke/hospital_c

2. Key Server يُبطل ClientKey_C فوراً:
   ├── إضافة المفتاح إلى CRL (Certificate Revocation List)
   ├── إلغاء جلسات QUIC النشطة مع مستشفى C
   └── تسجيل الإبطال في audit log

3. الـ Relay يتوقف عن قبول بيانات جديدة من مستشفى C:
   └── رفض أي DataSubmission من hospital_c

4. بيانات C السابقة:
   ├── هل نحذف ciphertexts القديمة؟
   │   خياران:
   │   أ. الحذف: Sponsor يطلب حذف ciphertexts من الـ Relay
   │   ب. الإبقاء: DPA يسمح باستخدام البيانات السابقة
   └── حسب DPA الموقّع مسبقاً

5. إشعار جميع الأطراف بالإبطال:
   ├── PI في مستشفى C يفقد الوصول إلى النتائج
   ├── النتائج المجمّعة تُعاد حسابها (pooled بدون C)
   └── Sponsor يُشعر IRB بالتغيير
```

### 7.2 سيناريو خرق أمني (Compromise)

```
إذا اخترق ClientKey_A ─── ماذا يحدث؟
──────────────────────────────────────

1. Sponsor يُصدر Emergency Revoke:
   ├── يُبطل ClientKey_A فوراً
   ├── يُدرّع Master Key (يولّد جديداً)
   └── يُصدِر ClientKey_A2 الجديد لـ Alice

2. إعادة تشفير بيانات Alice:
   └── تفك تشفير بيانات Alice القديمة بـ ClientKey_A (قبل الحذف)
   └── تعيد تشفيرها بـ ClientKey_A2 الجديد
   └── تُحمّل ciphertexts الجديدة إلى الـ Relay

3. تحقيق:
   └── يسحب Auditor سجل التدقيق ليرى متى ومَن استخدم ClientKey_A المخترق
```

## 8. سجل التدقيق | Audit Trail

### 8.1 ما يُسجّل | What Is Logged

| الحدث | يسجله | التفاصيل |
|-------|-------|---------|
| **إنشاء دراسة** | Key Server | study_id, sponsor, timestamp, parties |
| **توليد مفتاح** | Key Server | key_id, party_id, key_type, timestamp |
| **توزيع مفتاح** | Key Server | key_id, party_id, delivery_method |
| **رفع بيانات** | Relay | study_id, party_id, num_ciphertexts, size_bytes |
| **تنفيذ حساب** | Relay | study_id, operation, operands, result_hash |
| **فك تشفير** | Client (local) | study_id, result_id, timestamp → يُرسل إثباتاً لـ Relay |
| **إبطال مفتاح** | Key Server | key_id, reason, authorizer |
| **حذف بيانات** | Relay | study_id, num_ciphertexts, timestamp |
| **طلب وصول** | Key Server | requester_id, requested_result, approved_by |

### 8.2 من يراه؟ | Who Sees It?

```
الـ Audit Log مشفّر بمفتاح خاص بـ Auditor:
───────────────────────────────────────────
├── Auditor يستطيع فك تشفير log كاملاً
├── Sponsor يرى ملخصاً (من رفع ومتى — بدون ciphertexts)
├── PI يرى أحداث مؤسسته فقط
└── Relay لا يرى شيئاً (log مشفّر على Relay نفسه)
```

## 9. الاحتفاظ والتخلص | Retention & Destruction

### 9.1 الجدول الزمني الافتراضي | Default Timeline

```
    الدراسة          │     فترة     │     الاحتفاظ      │    الإتلاف
    ─────────────    │   الدراسة    │   (بعد النشر)    │
                     │              │                   │
    ┌─────────────┐  │ 6-12 شهر    │ 12-36 شهر        │ الشهر 48
    │ جمع البيانات │  │             │                   │
    ├─────────────┤  │              │                   │
    │ حساب النتائج│  │ 1-2 شهر     │                   │
    ├─────────────┤  │              │                   │
    │ مراجعة IRB  │  │ 1-2 شهر     │                   │
    ├─────────────┤  │              │                   │
    │ النشر       │  │ 3-6 شهر     │                   │
    ├─────────────┤  │              │                   │
    │ إتلاف       │  │              │                   │
    └─────────────┘  │              │                   │
                     └──────────────┴───────────────────┘
```

### 9.2 سياسات الاحتفاظ حسب نوع البيانات | Retention by Data Type

| نوع البيانات | مدة الاحتفاظ | الأساس القانوني |
|-------------|-------------|-----------------|
| **Plaintext الأصلي** (سجلات المرضى) | لا يغادر المستشفى أصلاً | سياسة المستشفى |
| **Ciphertexts** (على الـ Relay) | مدة الدراسة + 30 يوماً | DPA |
| **ClientKeys** | مدة الدراسة + 30 يوماً | حوكمة المفاتيح |
| **نتائج مشفّرة** | حسب DPA (عادة 1-3 سنوات بعد النشر) | 21 CFR Part 11 |
| **سجل التدقيق** | 6 سنوات (HIPAA) | HIPAA Privacy Rule |
| **مفاتيح الموسومة (Revoked)** | 30 يوماً بعد الإتلاف | سياسة الأمان |

### 9.3 آلية الإتلاف | Destruction Mechanism

```
المفاتيح:
────────────────────────
├── Key Server يدعم secure delete
├── PKCS#11 attributes: CKA_DESTROYABLE = TRUE
└── تأكيد: Key Server يُصدّر شهادة إتلاف موقّعة

البيانات (ciphertexts على الـ Relay):
────────────────────────────────────
├── حذف الملفات + مسح inodes (shred)
├── تأكيد: Relay يُصدّر تقرير حذف
├── اختياري: تخزين ciphertexts في encrypted volume
│   وإتلاف مفتاح الـ volume بدلاً من مسح البيانات
└── مناسب لأن ciphertext لا معنى له بدون المفتاح

سجل التدقيق:
───────────
├── لا يُحذف — يُحتفظ به 6 سنوات للامتثال
└── يُؤرشَف ويُختَم (Write-Once-Read-Many)
```

| **164.312(c)(1)** — Integrity | ZKP يثبت أن ciphertexts لم تُغيّر |
| **164.312(d)** — Person/Auth Authentication | Sponsor يوقّع كل مفتاح بمفتاحه الخاص |
| **164.312(e)(1)** — Transmission Security | QUIC + TLS 1.3 بين العقد |
| **164.312(b)** — Audit Controls | Audit Log لكل عملية فك تشفير |
| **164.310(d)(1)** — Disposal | إتلاف المفاتيح + شهادة موقّعة |
| **164.308(a)(5)(ii)(D)** — Password Management | لا — لا كلمات مرور (PKI) |
| **164.308(a)(1)(ii)(D)** — Information Access Management | Sponsor يُقرر من يشارك |

## 11. سيناريوهات الحوكمة حسب نوع الدراسة | Governance by Study Type

```
سيناريو:

───────
```

## 12. خارطة التنفيذ | Implementation Roadmap

### 12.1 V0.1 — أول عميل (الآن → 4-6 أسابيع)

```
ما نبنيه:
─────────
❌ Key Server — لا نبني بعد
❌ Per-Party Keys — لا تنطبق على أول عميل
✅ الدراسة الحالية: PI = Sponsor = Alice
✅ عقد DPA قانوني ينظّم المفاتيح
✅ إتلاف المفاتيح بنهاية الدراسة (يدوياً)

المخاطرة:
─────────
منخفضة — أول عميل يعرف أنه يختبر منتجاً جديداً
ودفعه مقابل القيمة، ليس مقابل الحوكمة الكاملة
```

### 12.2 V1.0 — Key Server + Per-Party Keys (شهر 2-4)

```
ما نبنيه:
─────────
✅ Key Server (Rust + Vault backend)
✅ Per-Party Key generation (N مفاتيح لكل دراسة)
✅ RBAC policy (أي دور يرى أي نتيجة)
✅ Audit Log (blockchain-like append-only log)
✅ Revocation API
✅ Destruction command

التكامل مع BDCP الحالي:
───────────────────────
├── bdcp-core: إضافة KeyPolicy + DecryptionRight إلى MessageKind
├── bdcp-node: إضافة KeyServer module (اختياري، feature gate)
├── bdcp-net: إضافة AuditRecord إلى DataStream
└── REST API (bdcp-api): endpoints للحوكمة
```

### 12.3 V2.0 — Threshold Decryption + HSM (شهر 12+)

```
ما نبنيه:
─────────
✅ Shamir Secret Sharing module
✅ Distributed Key Generation (DKG)
✅ HSM integration (PKCS#11 / YubiHSM)
✅ Zero-trust verification
✅ Multi-signature for decryption
```

### 12.4 ملخص التنفيذ

```
V0.1  ─── DPA قانوني + ClientKey واحد عند Sponsor
         │
         │ أول عميل (شهر 1-2)
         ▼
V1.0  ─── Key Server + RBAC + Per-Party Keys + Audit Log
         │
         │ 3+ عملاء (شهر 3-6)
         ▼
V1.5  ─── HSM support + multi-region Key Server
         │
         │ عملاء مؤسسيون (شهر 6-12)
         ▼
V2.0  ─── Threshold Decryption + DKG
         │
         │ وكالات حكومية (شهر 12+)
```

## 13. الخاتمة | Conclusion

### ما الذي تغير؟

```
قبل هذه الوثيقة:
─────────────────
BDCP = حل تشفيري قوي، لكنه غير قابل للاستخدام
       في بيئة تنظيمية.

المشكلة: "من يملك المفتاح؟" → لا إجابة.

بعد هذه الوثيقة:
────────────────
BDCP = منصة حوكمة متكاملة:
       ├── Per-Party Keys (كل طرف يرى ما يخصه)
       ├── Key Server (إدارة مركزية للمفاتيح)
       ├── RBAC (من يرى ماذا)
       ├── Audit Log (إثبات كل عملية)
       └── Revocation + Destruction (دورة حياة كاملة)

الإجابة: نموذج C — المفتاح ملك الدراسة،
         يُقسّم حسب الأدوار، ويُدار بـ Key Server.
```

### ما زالت هناك مخاطرة

```
الحوكمة التي وصفناها تفترض وجود Key Server موثوق.
لكن مَن يدير Key Server نفسه؟

الخيارات:
────────
1. Sponsor يديره — طبيعي، هو من يموّل
2. CRO طرف ثالث — أفضل: مستقل
3. Consortium مشترك — كل طرف لديه وصول جزئي
4. HSM مُدار عن بُعد — أعلى أمان

لأول عميل:
─────────
الخيار 1 (Sponsor يدير Key Server) كافٍ.
ننتقل للخيار 2 و3 مع نمو العملاء.
```
